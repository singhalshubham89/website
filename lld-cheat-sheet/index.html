Delivery Framework

How to spend a 45-minute low level design interview, including time to answer and time to write. The clock below fits any problem. Connect Four is one worked example of filling it in, not the script for every question.

45-minute clock

Talk through requirements, entities, and relationships before you write APIs. For a small problem, code starts around minute 15. A larger problem spends more of the middle on the model and the signatures, and less on a complete implementation.

PhaseClockTalkWriteWhat you do
Clarify0–54 min1 minFunctional requirements, actors, and the happy path. Non-functional requirements only if asked (concurrency, persistence). Write a short requirements note. Name what is out of scope.
Entities and relationships5–103 min2 minName the types and the state each one owns. One sentence per ownership edge. State each invariant in one line. If two splits are acceptable, say so. Do not write method bodies yet.
APIs10–152 min3 minPublic methods only, now that the types exist. Signatures, not bodies. Name the core method and what it returns: status, winner, or a result type.
Implement15–385 min18 minCore path in dependency order: types and enums, the state holder, the rule check, the orchestrator, a tiny driver. Narrate only the tricky parts while you type.
Harden38–433 min2 minInvalid input, a full or exhausted state, an operation after completion, and the terminal outcome (win, draw, or failure). Mention one extension. Do not code it unless asked.
Walkthrough43–452 min—One successful scenario and one rejected operation, using the code you actually wrote.

Worked timing: Connect Four

Same phases, filled in for a 6×7 gravity board. Parking Lot or Splitwise would name different entities before any signature. They would not start with Board.drop.

  • Clarify. Two players, gravity drop, connect four horizontal, vertical, and both diagonals, draw when the board is full, reject a bad column. Defer undo, AI, network, and persistence.
  • Entities and relationships. Board owns the cells. Game owns the turn and the status. WinChecker reads the board and does not own it. Color is the side.
  • APIs. Core method play(column) returns a result, not void. Board.drop returns the row where the disc landed.
  • Implement. Enums and status, board drop, win check from the last move, game turn loop, tiny driver.
  • Harden. Invalid column, full column, play after the game is over, draw.
  • Walkthrough. One winning sequence and one rejected move.
  • Win check. From the last disc, walk four directions. Each direction is O(K), and K is 4, so the check is constant for this ruleset. It is not O(1) for an arbitrary win length. A full-board scan is acceptable on a tiny board when time is short.

The reference design is in Connect Four.

Done checklist and traps

Stop when these are true:

  • Requirements and out-of-scope items are written down.
  • Entities and who owns what are written down before any signature.
  • The core method has a signature and a return value.
  • Invariants are stated, and the code enforces them.
  • The happy path and one failure path have been walked through.
  • One extension has been named, not implemented.

Traps that cost the round:

  • Naming a pattern for every class before any API exists.
  • Writing method bodies before the signatures are agreed.
  • Putting rules, storage, and printing in one orchestrator.

Concepts

Design principles, OOP, and the patterns that show up in Java LLD interviews. Each card is one idea, the interview smell, a bad snippet, and the fix for that same snippet.

Design principles

Single Responsibility

A type changes for one reason. In an interview that usually means storage, rules, and output are not the same class.

Interview smell: play validates the column, writes the grid, and prints the move.

Bad
class GameService {
    void play(int column, String color) {
        if (column < 0 || column > 6) return;
        grid[column] = color;
        System.out.println(color + " played " + column);
    }
    String[] grid = new String[7];
}
Fix
class Board {
    private final String[] columnTop = new String[7];
    void drop(int column, String color) {
        if (column < 0 || column > 6) {
            throw new IllegalArgumentException("column");
        }
        columnTop[column] = color;
    }
}
class Game {
    private final Board board = new Board();
    void play(int column, String color) {
        board.drop(column, color);
        System.out.println(color + " played " + column);
    }
}

Pros

  • GameService.play checks the column, assigns grid[column], and prints. After the split, Board.drop only checks the column and writes columnTop. Game.play only prints.
  • Changing the sentence color + " played " + column edits Game.play only. Changing how a disc is stored edits Board.drop only. Each type now has one reason to change.

Cons

  • One move is now Board plus Game. Before, it was the single method GameService.play.
  • To see the full move you read Game.play, then Board.drop. The bad play had the check, the write to grid[column], and the print in one method.

Over-engineering

  • A new type whose only line is if (column < 0 || column > 6). That check exists so columnTop[column] is a legal index. It changes for the same reason as Board.drop.
  • A new type whose only line is System.out.println. After board.drop, that print is already the job of Game.play. Nothing else calls it.

Split when you can name an edit that touches only the new type. Board passes: a storage edit does not touch the print. A column-check type or a print type fails: its only line is already the body of Board.drop or Game.play.

Open/Closed

Add a behavior by adding a type, not by editing a growing switch.

Interview smell: another case inside Pricer.total.

Bad
class Pricer {
    int total(String kind, int amount) {
        switch (kind) {
            case "none": return amount;
            case "half": return amount / 2;
            default: throw new IllegalArgumentException(kind);
        }
    }
}
Fix
interface PriceRule { int apply(int amount); }
class FullPrice implements PriceRule {
    public int apply(int amount) { return amount; }
}
class HalfPrice implements PriceRule {
    public int apply(int amount) { return amount / 2; }
}
class Pricer {
    int total(PriceRule rule, int amount) { return rule.apply(amount); }
}

Pros

  • Pricer.total calls rule.apply(amount). It has no case "half".
  • HalfPrice.apply returns amount / 2. That division is not inside Pricer.total.

Cons

  • The fix adds PriceRule, FullPrice, and HalfPrice. The bad version is one method, Pricer.total.
  • Reading Pricer.total does not show the "half" case. That case is HalfPrice.apply.

Over-engineering

  • A new type whose only line is return amount / 2. That line is already HalfPrice.apply.
  • A new type whose only line is return rule.apply(amount). That call is already Pricer.total.

Liskov Substitution

A subtype must honor the supertype's contract. Callers that use the parent type must still be correct.

Interview smell: Square extends Rectangle and setWidth also changes height, so area is no longer width times the height the caller set.

Bad
class Rectangle {
    int width; int height;
    void setWidth(int width) { this.width = width; }
    int area() { return width * height; }
}
class Square extends Rectangle {
    void setWidth(int width) { this.width = width; this.height = width; }
}
Fix
interface Shape { int area(); }
class Rectangle implements Shape {
    private final int width; private final int height;
    Rectangle(int width, int height) { this.width = width; this.height = height; }
    public int area() { return width * height; }
}
class Square implements Shape {
    private final int side;
    Square(int side) { this.side = side; }
    public int area() { return side * side; }
}

Pros

  • The bad Square.setWidth assigns this.height = width. The fix Square has no setWidth. area() uses the side from the constructor.
  • Square.area returns side * side. A later call cannot change height, because there is no setWidth.

Cons

  • The fix Rectangle also has no setWidth. The bad Rectangle had one.
  • width and height are constructor arguments and final. The bad fields could be assigned after new Rectangle.

Over-engineering

  • A new type whose only method returns side * side. That is already Square.area.
  • Putting setWidth on Shape. The fix Square has no setWidth. area uses the constructor side.

Interface Segregation

Clients should not implement methods they do not use.

Interview smell: a fat Machine interface forces a printer to stub scan and fax.

Bad
interface Machine {
    void print();
    void scan();
    void fax();
}
class SimplePrinter implements Machine {
    public void print() { /* ok */ }
    public void scan() { throw new UnsupportedOperationException(); }
    public void fax() { throw new UnsupportedOperationException(); }
}
Fix
interface Printer { void print(); }
interface Scanner { void scan(); }
class SimplePrinter implements Printer {
    public void print() { /* ok */ }
}
class Copier implements Printer, Scanner {
    public void print() { /* ok */ }
    public void scan() { /* ok */ }
}

Pros

  • SimplePrinter implements print() only. It has no scan method that throws.
  • The bad SimplePrinter.fax throws UnsupportedOperationException. The fix SimplePrinter has no fax method.

Cons

  • Copier lists Printer and Scanner. The old type listed one interface, Machine.
  • Copier must implement print and scan. The bad Machine also required fax on SimplePrinter.

Over-engineering

  • An interface that only declares fax. No fix class has fax. The bad SimplePrinter.fax threw UnsupportedOperationException, and the fix removed it.
  • A second interface that only declares print. Printer already does, and SimplePrinter implements print only.

Dependency Inversion

A high-level policy depends on an abstraction it owns. It does not construct a concrete store or client.

Interview smell: new MySqlOrderStore() inside the service, so the interview cannot swap a fake.

Bad
class OrderService {
    private final MySqlOrderStore store = new MySqlOrderStore();
    void place(String id) { store.insert(id); }
}
Fix
interface OrderStore { void insert(String id); }
class OrderService {
    private final OrderStore store;
    OrderService(OrderStore store) { this.store = store; }
    void place(String id) { store.insert(id); }
}

Pros

  • OrderService takes an OrderStore in its constructor. The bad field is new MySqlOrderStore().
  • place calls store.insert(id). The field type is OrderStore, not MySqlOrderStore.

Cons

  • The fix constructor is OrderService(OrderStore store). The bad class has no constructor parameter.
  • The bad field constructs MySqlOrderStore itself. The fix place cannot run until a store is passed in.

Over-engineering

  • A type whose only line is new MySqlOrderStore(). OrderService(OrderStore store) already receives the store.
  • An abstract class that only declares insert. interface OrderStore already declares insert, and it has no fields.

Composition over Inheritance

Vary a behavior by plugging in a collaborator. Do not add a subclass per variant.

Interview smell: EmailNotifier and SmsNotifier each exist only to implement send.

Bad
abstract class Notifier { abstract void send(String text); }
class EmailNotifier extends Notifier {
    void send(String text) { /* smtp */ }
}
class SmsNotifier extends Notifier {
    void send(String text) { /* sms */ }
}
Fix
interface Channel { void deliver(String text); }
class Notifier {
    private final List<Channel> channels;
    Notifier(List<Channel> channels) { this.channels = channels; }
    void send(String text) {
        for (Channel channel : channels) channel.deliver(text);
    }
}

Pros

  • Notifier.send loops channels and calls deliver. The bad version is two classes, EmailNotifier.send and SmsNotifier.send.
  • The list channels can hold more than one Channel. EmailNotifier.send and SmsNotifier.send are separate classes.

Cons

  • One email send is a Notifier plus a Channel. The bad version is the class EmailNotifier.
  • Notifier requires a List<Channel> in its constructor. EmailNotifier has no constructor parameter.

Over-engineering

  • A type whose only loop is for (Channel channel : channels) channel.deliver(text). That loop is already Notifier.send.
  • A subclass of Notifier per channel. EmailNotifier and SmsNotifier were that split. The list channels already holds more than one Channel.

Ownership mistakes, such as Game extends Board, are covered under Composition.

DRY, KISS, and YAGNI

One copy of a rule, the simplest structure that enforces it, and no framework for a requirement you do not have.

Interview smell: the column check is pasted twice, and a rule engine exists for that single check.

Bad
class Game {
    void play(int column) {
        if (column < 0 || column >= 7) return;
        drop(column);
    }
    boolean canPlay(int column) {
        return column >= 0 && column < 7;
    }
}
class RuleEngine {
    boolean eval(String script) { return true; }
}
Fix
class Game {
    private static final int COLS = 7;
    boolean playable(int column) {
        return column >= 0 && column < COLS;
    }
    void play(int column) {
        if (!playable(column)) throw new IllegalArgumentException("column");
        drop(column);
    }
    void drop(int column) { /* board */ }
}

Pros

  • The fix names the limit once, as COLS, and playable uses it. The bad play and canPlay each write the literal 7.
  • play calls playable before drop. The bad play repeats the column < 0 test that canPlay already has.

Cons

  • The bad file also has RuleEngine.eval, which returns true and is not called. The fix has no RuleEngine.
  • The fix play throws IllegalArgumentException. The bad play hits return and does not call drop.

Over-engineering

  • RuleEngine.eval returns true and nothing calls it. The column rule is already playable.
  • A type whose only line is column >= 0 && column < COLS. That expression is already playable.

OOP

Encapsulation

Keep the representation private. Callers use operations that preserve invariants.

Interview smell: board.cells[3][0] = Color.RED writes the public array.

Bad
class Board {
    public Color[][] cells = new Color[6][7];
}
// caller
board.cells[3][0] = Color.RED;
Fix
class Board {
    private final Color[][] cells = new Color[6][7];
    int drop(int column, Color color) {
        for (int row = 0; row < cells.length; row++) {
            if (cells[row][column] == null) {
                cells[row][column] = color;
                return row;
            }
        }
        throw new IllegalStateException("full");
    }
    Color cellAt(int row, int col) { return cells[row][col]; }
}

Pros

  • board.cells[3][0] = Color.RED does not compile. A disc can only land through drop, in the lowest empty row.
  • drop writes cells[row][column] only when that cell is null, starting at row 0.

Cons

  • drop does not check column. cells[row][column] throws when column is 7.
  • cellAt returns cells[row][col]. A caller can read a cell. The assignment cells[3][0] = Color.RED is still not available.

Over-engineering

  • A type whose only field is one Color. drop already assigns cells[row][column], and cellAt already returns it.
  • A type whose only method is the for loop inside drop. That loop is how drop finds the null cell.

Abstraction

Use an interface when types share a contract and no fields. Use an abstract class only when subclasses share state.

Interview smell: an abstract base forces a file path onto an HTTP exporter that has no file.

Bad
abstract class Exporter {
    String filePath;
    abstract void export(String body);
}
class HttpExporter extends Exporter {
    void export(String body) { /* POST, filePath unused */ }
}
Fix
interface Exporter { void export(String body); }
abstract class FileExporter implements Exporter {
    protected final String filePath;
    FileExporter(String filePath) { this.filePath = filePath; }
}
class HttpExporter implements Exporter {
    public void export(String body) { /* POST */ }
}

Pros

  • HttpExporter has no filePath field. The old abstract class forced one onto it.
  • The bad HttpExporter.export extends a class that declares filePath. The fix export takes only body.

Cons

  • FileExporter stores filePath. HttpExporter implements Exporter and has no filePath field.
  • FileExporter's constructor requires a filePath. HttpExporter has no such constructor.

Over-engineering

  • An abstract class that HttpExporter extends and that has no fields. HttpExporter already implements Exporter, and export takes only body.
  • FileExporter exists because subclasses share filePath. A second base for HttpExporter has no field to share.

Inheritance

Inherit to specialize a real is-a contract. Do not inherit to reuse a method or a collection.

Interview smell: ParkingLot extends ArrayList and park returns add(car).

Bad
class ParkingLot extends ArrayList<Car> {
    boolean park(Car car) { return add(car); }
}
Fix
class ParkingLot {
    private final List<Car> spots = new ArrayList<>();
    boolean park(Car car) {
        if (spots.size() == 10) return false;
        return spots.add(car);
    }
}

Pros

  • The fix park returns false when spots.size() == 10. The bad park returns add(car) with no size check.
  • spots is private. The bad ParkingLot extends ArrayList, so add is a public method on the lot.

Cons

  • The fix park calls spots.size() and spots.add. The bad park calls add inherited from ArrayList.
  • The 11th park returns false because of spots.size() == 10. The bad add would still append that car.

Over-engineering

  • A subclass whose only change is the 10 in spots.size() == 10. That check is already inside park.
  • A type that only calls spots.add. park already calls spots.add after the size check.

Polymorphism

The caller asks the object to do the work. It does not branch on the concrete class.

Interview smell: instanceof King and instanceof Knight in the game loop.

Bad
class Rules {
    boolean attacks(Piece piece, int toRow, int toCol) {
        if (piece instanceof King) return distance(piece, toRow, toCol) <= 1;
        if (piece instanceof Knight) return knightJump(piece, toRow, toCol);
        return false;
    }
}
Fix
interface Piece {
    boolean attacks(int toRow, int toCol);
}
class King implements Piece {
    private final int row; private final int col;
    King(int row, int col) { this.row = row; this.col = col; }
    public boolean attacks(int toRow, int toCol) {
        int dr = Math.abs(toRow - row);
        int dc = Math.abs(toCol - col);
        return dr <= 1 && dc <= 1 && (dr + dc) > 0;
    }
}
class Rules {
    boolean legal(Piece piece, int toRow, int toCol) {
        return piece.attacks(toRow, toCol);
    }
}

Pros

  • The bad Rules.attacks has instanceof King. The fix Rules.legal calls piece.attacks and has no instanceof.
  • King.attacks uses Math.abs(toRow - row). That math is not in Rules.legal.

Cons

  • King.attacks compares toRow and toCol with its own row and col. Rules.legal does not look at any other piece.
  • The bad Rules.attacks also has instanceof Knight. The fix Rules.legal has no knight branch.

Over-engineering

  • A type whose only lines are Math.abs(toRow - row) and Math.abs(toCol - col). Those lines are already King.attacks.
  • Rules.legal already calls piece.attacks. A second rules object beside King repeats that method.

Composition

A game has a board. It is not a board. Has-a keeps each type's invariant in that type.

Interview smell: class Game extends Board so play can call drop as if the match were the grid.

Bad
class Game extends Board {
    void play(int column, Color color) { drop(column, color); }
}
Fix
class Game {
    private final Board board;
    Game(Board board) { this.board = board; }
    void play(int column, Color color) { board.drop(column, color); }
}

Pros

  • The fix Game has a Board field. The bad Game extends Board.
  • The fix constructor is Game(Board board). The bad Game has no constructor and no Board field.

Cons

  • play calls board.drop. The subclass version called drop directly.
  • A Game cannot be constructed without a Board. The bad class is constructed as a Board subclass.

Over-engineering

  • A type whose only field is Board and whose only call is board.drop. That field and call are already Game.
  • A third type between Game and Board. play already calls board.drop. Game extends Board was the other mistake, not a missing layer.

Design patterns

Builder

Build an object with several optional fields without a telescoping constructor.

Interview smell: new GameConfig(6, 7, 4, false, false, null).

Bad
class GameConfig {
    GameConfig(int rows, int cols, int win, boolean undo, boolean bot, String name) {}
}
new GameConfig(6, 7, 4, false, false, null);
Fix
class GameConfig {
    final int rows; final int cols; final int winLength;
    private GameConfig(int rows, int cols, int winLength) {
        this.rows = rows; this.cols = cols; this.winLength = winLength;
    }
    static Builder builder() { return new Builder(); }
    static class Builder {
        private int rows = 6; private int cols = 7; private int winLength = 4;
        Builder rows(int rows) { this.rows = rows; return this; }
        Builder cols(int cols) { this.cols = cols; return this; }
        Builder winLength(int winLength) { this.winLength = winLength; return this; }
        GameConfig build() { return new GameConfig(rows, cols, winLength); }
    }
}

Pros

  • The fix has methods named rows, cols, and winLength. The bad call is new GameConfig(6, 7, 4, false, false, null), and those parameters have no names at the call.
  • rows, cols, and winLength each return this. build calls new GameConfig(rows, cols, winLength).

Cons

  • The bad constructor takes undo, bot, and name as well as the three ints. The fix Builder only has rows, cols, and winLength.
  • The builder fields start at rows = 6, cols = 7, and winLength = 4. The bad call must pass all six arguments.

Over-engineering

  • Builder when the caller always sets rows, cols, and winLength. Those methods only forward to new GameConfig(rows, cols, winLength).
  • The call that needs a builder is new GameConfig(6, 7, 4, false, false, null). Three required ints can stay the constructor GameConfig(int rows, int cols, int winLength).

Factory Method

Hide the concrete class behind a method when construction depends on a kind, and callers should not switch on that kind.

Interview smell: the driver contains if (kind.equals("line")) new LineChecker().

Bad
WinChecker checker;
if (kind.equals("line")) checker = new LineChecker();
else checker = new AnyDirectionChecker();
Fix
class WinCheckers {
    static WinChecker create(String kind) {
        if (kind.equals("line")) return new LineChecker();
        return new AnyDirectionChecker();
    }
}
WinChecker checker = WinCheckers.create(kind);

Pros

  • The kind.equals("line") branch lives in WinCheckers.create. The call site is WinCheckers.create(kind).
  • The bad snippet puts that if next to WinChecker checker. The fix call site is one line, WinCheckers.create(kind).

Cons

  • create still contains if (kind.equals("line")). The bad snippet has that same if at the call site.
  • When kind is not "line", create returns new AnyDirectionChecker(). The bad else branch does the same.

Over-engineering

  • A type whose only line is new LineChecker(). WinCheckers.create already returns that when kind.equals("line").
  • A second factory for AnyDirectionChecker. The other branch in create already returns new AnyDirectionChecker().

Singleton

One instance is a process-wide resource. A match, a board, or an order is not one of those.

Interview smell: getInstance returns the one INSTANCE.

Bad
class Game {
    private static final Game INSTANCE = new Game();
    static Game getInstance() { return INSTANCE; }
    void play(int column) { /* mutates the only board */ }
}
Fix
class Game {
    private final Board board;
    Game(Board board) { this.board = board; }
    void play(int column) { board.drop(column, Color.RED); }
}
Game match = new Game(new Board(6, 7));

Pros

  • The fix builds new Game(new Board(6, 7)). The bad getInstance returns the one INSTANCE created by new Game().
  • new Game(new Board(6, 7)) passes a Board. getInstance takes no argument.

Cons

  • The bad getInstance returns INSTANCE. The fix caller writes new Game(new Board(6, 7)).
  • INSTANCE is new Game() with no Board. The fix constructor is Game(Board board).

Over-engineering

  • getInstance and INSTANCE for one match. The fix caller writes new Game(new Board(6, 7)), and that line can build a second game.
  • A type whose only line is new Game(new Board(6, 7)). The caller already writes that line.

Adapter

Wrap a type you do not control so the rest of the design keeps your interface.

Interview smell: Game.play calls guessRow and then vendor.placeDisc(column, row).

Bad
class Game {
    private final VendorBoard vendor;
    void play(int column) {
        int row = guessRow(column);
        vendor.placeDisc(column, row);
    }
}
Fix
interface BoardPort { int drop(int column, Color color); }
class VendorBoardAdapter implements BoardPort {
    private final VendorBoard vendor;
    VendorBoardAdapter(VendorBoard vendor) { this.vendor = vendor; }
    public int drop(int column, Color color) {
        return vendor.placeDisc(column, color.name());
    }
}

Pros

  • VendorBoardAdapter.drop takes (column, color) and calls vendor.placeDisc(column, color.name()). The bad Game.play calls placeDisc(column, row) after guessRow.
  • drop's second argument is Color color. The bad placeDisc receives the row from guessRow.

Cons

  • drop still calls placeDisc. The adapter changes the method the caller sees, and the vendor method stays.
  • The fix type is VendorBoardAdapter. The bad type that calls placeDisc is Game.

Over-engineering

  • A second wrapper whose only call is vendor.placeDisc. That call is already VendorBoardAdapter.drop.
  • A type whose only line is color.name(). drop already passes color.name() into placeDisc.

Decorator

Add a concern by wrapping the same interface. Do not create a subclass for each combination.

Interview smell: LoggedGame extends Game and prints inside play.

Bad
class LoggedGame extends Game {
    void play(int column) {
        System.out.println(column);
        super.play(column);
    }
}
Fix
interface Match { MoveResult play(int column); }
class LoggingMatch implements Match {
    private final Match next;
    LoggingMatch(Match next) { this.next = next; }
    public MoveResult play(int column) {
        MoveResult result = next.play(column);
        System.out.println(column + " -> " + result);
        return result;
    }
}

Pros

  • LoggingMatch.play prints column, then calls next.play(column). The bad version prints inside LoggedGame, which extends Game.
  • LoggingMatch stores Match next and returns the MoveResult from next.play.

Cons

  • The bad version is one class, LoggedGame. The fix adds Match and LoggingMatch.
  • LoggingMatch.play prints column + " -> " + result. LoggedGame.play prints column and then calls super.play.

Over-engineering

  • A subclass of LoggingMatch whose only added line is another System.out.println. LoggingMatch.play already prints column + " -> " + result.
  • A wrapper that only calls next.play and prints nothing. LoggingMatch already stores Match next and returns next.play.

Facade

Offer one method for the operation the interviewer asked for. Keep the rules in the types behind it.

Interview smell: board.drop, winChecker.isWin, and board.isFull are written at the call site.

Bad
int row = board.drop(column, turn);
if (winChecker.isWin(board, row, column, turn)) status = WIN;
else if (board.isFull()) status = DRAW;
else turn = other(turn);
Fix
class Game {
    MoveResult play(int column) {
        int row = board.drop(column, turn);
        if (winChecker.isWin(board, row, column, turn)) status = WIN;
        else if (board.isFull()) status = DRAW;
        else turn = other(turn);
        return MoveResult.of(status);
    }
}

Pros

  • drop, isWin, and isFull are inside play. The bad snippet is those same three calls written at the call site, where the isFull line can be skipped.
  • After those checks, play assigns status or calls other(turn), then returns MoveResult.of(status).

Cons

  • The fix play uses board, winChecker, status, and turn, and this class body does not declare them.
  • The bad snippet has no method named play. The three calls sit at the call site.

Over-engineering

  • A type whose only line is play(column). drop, isWin, and isFull are already inside Game.play.
  • A separate type for isWin and another for isFull. play already runs both before MoveResult.of(status).

Connect Four uses Game.play as this facade and leaves the scan in WinChecker.

Strategy

Swap an algorithm without subclassing the owner. Game status is usually an enum. A bot's move choice is a strategy.

Interview smell: if (mode.equals("bot")) inside play to pick a column, next to the rules.

Bad
class Game {
    int play(String mode) {
        if (mode.equals("bot")) return 3;
        return readColumn();
    }
    int readColumn() { return 0; }
}
Fix
interface MoveStrategy { int chooseColumn(Board board, Color color); }
class CenterBot implements MoveStrategy {
    public int chooseColumn(Board board, Color color) { return board.cols() / 2; }
}
class Game {
    private final MoveStrategy moves;
    Game(MoveStrategy moves) { this.moves = moves; }
    int play(Board board, Color color) {
        return moves.chooseColumn(board, color);
    }
}

Pros

  • play returns moves.chooseColumn(board, color). It has no mode.equals("bot").
  • CenterBot.chooseColumn returns board.cols() / 2. The bad bot branch returns 3.

Cons

  • The bad play calls readColumn() directly. The fix Game stores a MoveStrategy field, and play calls moves.chooseColumn.
  • The fix constructor requires a MoveStrategy. The bad play takes a String mode.

Over-engineering

  • One CenterBot when chooseColumn only returns board.cols() / 2 and play only calls moves.chooseColumn. That division can live in play until a second chooseColumn exists.
  • The bad play returned 3 when mode.equals("bot"). A strategy class for that single return is an extra type around one number.

Observer

The game tells interested objects that a move happened. It does not construct every view.

Interview smell: play calls printer.print and scoreboard.record, and the next view is another line in Game.

Bad
class Game {
    private final Printer printer;
    private final Scoreboard scoreboard;
    void play(int column) {
        printer.print(column);
        scoreboard.record(column);
    }
}
Fix
interface MoveListener { void onMove(int column, MoveResult result); }
class Game {
    private final List<MoveListener> listeners = new ArrayList<>();
    void addListener(MoveListener listener) { listeners.add(listener); }
    void notifyMove(int column, MoveResult result) {
        for (MoveListener listener : listeners) listener.onMove(column, result);
    }
}

Pros

  • notifyMove loops listeners and calls onMove. The bad play calls scoreboard.record(column) by name.
  • addListener adds to listeners. notifyMove is the method that walks that list.

Cons

  • The bad play calls printer.print and scoreboard.record directly. The fix adds listeners, addListener, and notifyMove.
  • The bad play takes only column. notifyMove also takes a MoveResult.

Over-engineering

  • A type whose only lines are listeners.add and the for loop. Those lines are already addListener and notifyMove.
  • A separate listener type for printer.print and another for scoreboard.record. Both can be MoveListener.onMove.

State

Use the State pattern when each status has different behavior. Use an enum when the status is a label and a guard.

Interview smell: WonState.onPlay calls game.reject().

Bad
interface Status { void onPlay(Game game); }
class WonState implements Status {
    public void onPlay(Game game) { game.reject(); }
}
Fix
enum GameStatus { IN_PROGRESS, WIN, DRAW }
class Game {
    private GameStatus status = GameStatus.IN_PROGRESS;
    MoveResult play(int column) {
        if (status != GameStatus.IN_PROGRESS) {
            return MoveResult.failed(PlayFailure.GAME_OVER);
        }
        return MoveResult.inProgress();
    }
}

Pros

  • play returns MoveResult.failed(PlayFailure.GAME_OVER) when status != GameStatus.IN_PROGRESS. The bad WonState.onPlay calls game.reject().
  • When status is IN_PROGRESS, play returns MoveResult.inProgress().

Cons

  • The fix is an enum GameStatus and one if in play. The bad version is the interface Status and the class WonState.
  • The bad block shows only WonState. The fix enum lists IN_PROGRESS, WIN, and DRAW.

Over-engineering

  • WonState.onPlay only calls game.reject(). The fix play returns MoveResult.failed(PlayFailure.GAME_OVER) when status != GameStatus.IN_PROGRESS.
  • A class for WIN and a class for DRAW. The enum already lists IN_PROGRESS, WIN, and DRAW, and play has one if.

Concurrency

Use these only when the problem implies shared mutable state or background work. A single-threaded Connect Four match does not need a lock. Each card is the concept, the problem, a Java fix, and the trade-off.

Race on shared mutable state

Concept. Two threads run a read-modify-write on the same fields. The interleaving loses an update.

Problem. Two calls to play both read an empty cell and both write it. One disc disappears, or the turn flips twice.

Solution. One lock around the whole move, not around each array write.

Bad
class Game {
    void play(int column, Color color) {
        board.drop(column, color);
        turn = other(turn);
    }
    Color other(Color current) {
        return current == Color.RED ? Color.YELLOW : Color.RED;
    }
}
Fix
class Game {
    synchronized void play(int column, Color color) {
        board.drop(column, color);
        turn = other(turn);
    }
}

Pros

  • turn = other(turn) is inside synchronized play. The second thread runs that line only after the first thread has left play.
  • other returns YELLOW when current is RED, and RED otherwise. Both board.drop and that assignment are inside the synchronized method.

Cons

  • The shown play is the only method marked synchronized.
  • The bad play is not synchronized, so two calls can both reach turn = other(turn).

volatile and AtomicInteger

Concept. volatile publishes a single write so other threads see it. It does not make a read-modify-write atomic. AtomicInteger does.

Problem. A stop flag written by one thread stays invisible, or count++ on a volatile int loses increments.

Solution. volatile for the flag. AtomicInteger for the counter.

Bad
class Scoreboard {
    volatile int games;
    void recordWin() { games++; }
}
Fix
class Scoreboard {
    private final AtomicInteger games = new AtomicInteger();
    private volatile boolean closed;
    void recordWin() { games.incrementAndGet(); }
    void close() { closed = true; }
    boolean isClosed() { return closed; }
}

Pros

  • recordWin calls games.incrementAndGet(). The bad recordWin does games++ on a volatile int.
  • closed is volatile. close sets it to true, and isClosed returns closed.

Cons

  • close writes closed. recordWin writes games. A reader can see closed == true while games still has the old count.
  • games++ reads and writes games. incrementAndGet is the call the fix uses instead.

Deadlock and lock order

Concept. Two threads each hold a lock the other needs. Neither proceeds.

Problem. play locks the board, then the log. The logger locks the log, then the board, to print the grid.

Solution. Both paths acquire locks in the same order. Prefer one lock when the critical section is the move.

Bad
void play() {
    synchronized (board) {
        synchronized (log) { log.add("move"); }
    }
}
void flush() {
    synchronized (log) {
        synchronized (board) { log.add(board.toString()); }
    }
}
Fix
void play() {
    synchronized (board) {
        synchronized (log) { log.add("move"); }
    }
}
void flush() {
    synchronized (board) {
        synchronized (log) { log.add(board.toString()); }
    }
}

Pros

  • play and flush both lock board, then log. Neither waits while holding the lock the other needs.
  • The bad flush locks log and then board. The fix flush locks board and then log, the same order as play.

Cons

  • play calls log.add while it holds board. flush also locks board before log.
  • Both methods still use two synchronized blocks. The fix does not remove the inner lock on log.

HashMap and ConcurrentHashMap

Concept. HashMap is not safe for concurrent writers. ConcurrentHashMap is safe for individual map operations.

Problem. A shared session or score cache resizes while another thread reads it. That can loop or lose entries. A check-then-act around containsKey is still a race even on the concurrent map.

Solution. Use ConcurrentHashMap and an atomic method such as putIfAbsent or compute.

Bad
class SessionCache {
    private final Map<String, Session> sessions = new HashMap<>();
    Session getOrCreate(String id) {
        if (!sessions.containsKey(id)) sessions.put(id, new Session(id));
        return sessions.get(id);
    }
}
Fix
class SessionCache {
    private final ConcurrentMap<String, Session> sessions = new ConcurrentHashMap<>();
    Session getOrCreate(String id) {
        return sessions.computeIfAbsent(id, Session::new);
    }
}

Pros

  • getOrCreate returns computeIfAbsent(id, Session::new). The bad method calls containsKey and then put as two separate steps.
  • The fix map is a ConcurrentHashMap. The bad map is a HashMap.

Cons

  • Session::new must be a constructor that takes the id string. The bad method writes new Session(id) in the method body.
  • Two threads can both pass containsKey before either put. computeIfAbsent is one call, so that gap is gone.

BlockingQueue

Concept. A bounded queue hands work from producers to consumers and blocks instead of dropping or spinning.

Problem. log calls writeDisk on the same thread that called log, and lines is an ArrayList.

Solution. log calls lines.put on an ArrayBlockingQueue. drain calls take and then writeDisk.

Bad
class GameLogger {
    private final List<String> lines = new ArrayList<>();
    void log(String line) { lines.add(line); writeDisk(line); }
    void writeDisk(String line) { /* slow */ }
}
Fix
class GameLogger {
    private final BlockingQueue<String> lines = new ArrayBlockingQueue<>(1000);
    void log(String line) throws InterruptedException { lines.put(line); }
    void drain() throws InterruptedException {
        writeDisk(lines.take());
    }
    void writeDisk(String line) { /* slow, off the player thread */ }
}

Pros

  • log calls lines.put(line) and returns. writeDisk runs in drain, after lines.take().
  • The bad log calls lines.add and writeDisk in the same method. The fix log only calls put.

Cons

  • The queue is new ArrayBlockingQueue<>(1000). The 1001st log call blocks inside put.
  • drain calls lines.take(). take waits when the queue has no line.

ReadWriteLock

Concept. Many readers can hold the read lock together. A writer excludes everyone.

Problem. A spectator view locks the same way as play, so reads of a stable board queue behind each other.

Solution. Read lock for a snapshot of the board. Write lock for play.

Bad
class Game {
    synchronized String view() { return board.render(); }
    synchronized MoveResult play(int column) { return MoveResult.inProgress(); }
}
Fix
class Game {
    private final ReadWriteLock lock = new ReentrantReadWriteLock();
    String view() {
        lock.readLock().lock();
        try { return board.render(); }
        finally { lock.readLock().unlock(); }
    }
    MoveResult play(int column) {
        lock.writeLock().lock();
        try { return MoveResult.inProgress(); }
        finally { lock.writeLock().unlock(); }
    }
}

Pros

  • Two view() calls run at the same time. Two synchronized view() calls do not.
  • view locks readLock and unlocks it in finally. play locks writeLock.

Cons

  • If almost every call is play, synchronized is the shorter method and the reads were not the bottleneck.
  • The fix view and play are longer than the two synchronized methods in the bad class.

Immutable shared state

Concept. An object that never changes after publication needs no lock to be read.

Problem. A listener keeps the MoveResult and a later setter changes the winner it already displayed.

Solution. Final fields, no setters, and a defensive copy if you must expose an array.

Bad
class MoveResult {
    GameStatus status;
    Color winner;
    void setWinner(Color winner) { this.winner = winner; }
}
Fix
final class MoveResult {
    private final GameStatus status;
    private final Color winner;
    MoveResult(GameStatus status, Color winner) {
        this.status = status;
        this.winner = winner;
    }
    GameStatus status() { return status; }
    Color winner() { return winner; }
}

Pros

  • The fix class has no setWinner. The bad setWinner assigns this.winner.
  • winner() returns winner. Nothing in the fix assigns winner after the constructor.

Cons

  • The fix fields status and winner are final. The bad fields are not final.
  • A different winner needs a new MoveResult. The bad class could call setWinner on the same object.

ExecutorService

Concept. Submit work to a pool. Do not start a raw thread per task.

Problem. Each logged move does new Thread(...).start(). Under a burst you create more threads than the machine can run, and nothing shuts them down.

Solution. One bounded pool owned by the logger or the app, shut down when the game ends.

Bad
void logAsync(String line) {
    new Thread(() -> writeDisk(line)).start();
}
void writeDisk(String line) { /* I/O */ }
Fix
class GameLogger {
    private final ExecutorService pool = Executors.newFixedThreadPool(1);
    void logAsync(String line) { pool.submit(() -> writeDisk(line)); }
    void close() { pool.shutdown(); }
    void writeDisk(String line) { /* I/O */ }
}

Pros

  • logAsync calls pool.submit. The bad logAsync calls new Thread and start.
  • The pool is Executors.newFixedThreadPool(1). Each submit uses that pool.

Cons

  • The fix has close, which calls pool.shutdown(). The bad snippet has no shutdown.
  • The bad new Thread is not stored, so there is no method in that snippet that stops it.

Lazy initialization

Concept. Create an expensive shared object on first use, safely. A game is not that object. A process-wide logger might be.

Problem. A naive null check creates two loggers. Classic double-checked locking without volatile can publish a logger whose fields are still at defaults.

Solution. The static holder class. The JVM initializes it once, on first touch.

Bad
class Log {
    private static Log instance;
    static Log get() {
        if (instance == null) {
            synchronized (Log.class) {
                if (instance == null) instance = new Log();
            }
        }
        return instance;
    }
}
Fix
class Log {
    private Log() {}
    private static class Holder {
        static final Log INSTANCE = new Log();
    }
    static Log get() { return Holder.INSTANCE; }
}

Pros

  • get returns Holder.INSTANCE. new Log() is the static final field, not an assignment inside synchronized.
  • Holder.INSTANCE is static final, so that new Log() runs when Holder is first used.

Cons

  • Log() is private and get returns Holder.INSTANCE. A caller cannot pass a different Log.
  • Both get methods take no argument. The bad one assigns instance = new Log() inside synchronized.

Case Studies

One filled reference, then empty slots that use the same headings. Grid games later should follow Connect Four instead of growing a second board implementation.

Connect Four

Problem

Two players take turns dropping a disc into a column of a 6×7 board. Gravity pulls the disc to the lowest empty row. A player wins by connecting four discs horizontally, vertically, or diagonally. The game draws when the board is full and nobody has four.

Out of scope in the core code: AI, undo, network, and persistence.

Invariants

  • A disc occupies one cell.
  • A drop lands in the lowest empty row of that column. Row 0 is the bottom.
  • A column rejects a drop when it is full.
  • No move is accepted after a win or a draw.

Classes and APIs

Core method: Game.play(column) returns a MoveResult with the status and, on a win, the winner. Failures are INVALID_COLUMN, COLUMN_FULL, and GAME_OVER. They are not silent no-ops.

  • Color is the side. There is no Player class. A name is not part of the rules, and a class that only stores one would not earn its file.
  • Board.drop(column, color) owns the grid. It does not know whose turn it is, and it does not expose the array.
  • WinChecker.isWin(board, lastRow, lastCol, piece) walks four directions, at most K cells each. That is O(K) per direction. With K fixed at 4 it is constant. It is not O(1) for an arbitrary K. A full-board scan is acceptable on this tiny board if you are out of time.
  • Game owns the turn, the status, and the call order: reject if over, drop, win, draw, switch turn.

Design decisions

Reference split, used in the code. Game is the orchestrator. Board answers "where does this disc land?" WinChecker answers "did this disc complete K in a row?" Pick this when you want the turn and the terminal state out of the grid, which is the usual interview split.

Second acceptable split. A richer Board validates the column, applies gravity, and returns the placed row or a drop failure. Game still owns the turn, the win, and the draw. Pick this when you want every grid invariant in one type and the match object to stay thin. Do not also put the turn inside Board unless the board is the whole product. Either split is fine. Mixing both, so that main drops and also checks wins, is the one to avoid.

GameStatus is an enum: IN_PROGRESS, WIN, DRAW. State classes would only restate that guard. A bot later is a MoveStrategy, not a status.

Implementation

One compilation unit for the cheat sheet. In the interview these are separate types. ConnectFourDemo is the only public class so the file can be ConnectFourDemo.java.

enum Color { RED, YELLOW }

enum GameStatus { IN_PROGRESS, WIN, DRAW }

enum PlayFailure { INVALID_COLUMN, COLUMN_FULL, GAME_OVER }

final class MoveResult {
    private final GameStatus status;
    private final Color winner;
    private final PlayFailure failure;

    private MoveResult(GameStatus status, Color winner, PlayFailure failure) {
        this.status = status;
        this.winner = winner;
        this.failure = failure;
    }

    static MoveResult inProgress() {
        return new MoveResult(GameStatus.IN_PROGRESS, null, null);
    }

    static MoveResult win(Color winner) {
        return new MoveResult(GameStatus.WIN, winner, null);
    }

    static MoveResult draw() {
        return new MoveResult(GameStatus.DRAW, null, null);
    }

    static MoveResult failed(GameStatus status, PlayFailure failure) {
        return new MoveResult(status, null, failure);
    }

    public String toString() {
        if (failure != null) return "failed " + failure + " while " + status;
        if (winner != null) return status + " " + winner;
        return status.name();
    }
}

final class Board {
    private final int rows;
    private final int cols;
    private final Color[][] cells; // row 0 is the bottom

    Board(int rows, int cols) {
        if (rows < 1 || cols < 1) throw new IllegalArgumentException("size");
        this.rows = rows;
        this.cols = cols;
        this.cells = new Color[rows][cols];
    }

    Drop drop(int column, Color color) {
        if (column < 0 || column >= cols) return Drop.failed(PlayFailure.INVALID_COLUMN);
        for (int row = 0; row < rows; row++) {
            if (cells[row][column] == null) {
                cells[row][column] = color;
                return Drop.placed(row);
            }
        }
        return Drop.failed(PlayFailure.COLUMN_FULL);
    }

    Color cellAt(int row, int col) { return cells[row][col]; }
    int rows() { return rows; }
    int cols() { return cols; }

    boolean isFull() {
        for (int col = 0; col < cols; col++) {
            if (cells[rows - 1][col] == null) return false;
        }
        return true;
    }

    static final class Drop {
        final Integer row;
        final PlayFailure failure;

        private Drop(Integer row, PlayFailure failure) {
            this.row = row;
            this.failure = failure;
        }

        static Drop placed(int row) { return new Drop(row, null); }
        static Drop failed(PlayFailure failure) { return new Drop(null, failure); }
        boolean ok() { return failure == null; }
    }
}

final class WinChecker {
    private final int winLength;

    WinChecker(int winLength) {
        if (winLength < 2) throw new IllegalArgumentException("winLength");
        this.winLength = winLength;
    }

    // Four directions from the last disc. Each direction is O(K), K = winLength.
    boolean isWin(Board board, int lastRow, int lastCol, Color piece) {
        int[][] directions = {{0, 1}, {1, 0}, {1, 1}, {1, -1}};
        for (int[] direction : directions) {
            int count = 1;
            count += count(board, lastRow, lastCol, direction[0], direction[1], piece);
            count += count(board, lastRow, lastCol, -direction[0], -direction[1], piece);
            if (count >= winLength) return true;
        }
        return false;
    }

    private int count(Board board, int row, int col, int dr, int dc, Color piece) {
        int seen = 0;
        for (int step = 1; step < winLength; step++) {
            int nextRow = row + dr * step;
            int nextCol = col + dc * step;
            if (nextRow < 0 || nextCol < 0 || nextRow >= board.rows() || nextCol >= board.cols()) break;
            if (board.cellAt(nextRow, nextCol) != piece) break;
            seen++;
        }
        return seen;
    }
}

final class Game {
    private final Board board;
    private final WinChecker winChecker;
    private GameStatus status = GameStatus.IN_PROGRESS;
    private Color turn = Color.RED;
    private Color winner;

    Game(Board board, WinChecker winChecker) {
        this.board = board;
        this.winChecker = winChecker;
    }

    MoveResult play(int column) {
        if (status != GameStatus.IN_PROGRESS) {
            return MoveResult.failed(status, PlayFailure.GAME_OVER);
        }
        Board.Drop drop = board.drop(column, turn);
        if (!drop.ok()) return MoveResult.failed(status, drop.failure);
        if (winChecker.isWin(board, drop.row, column, turn)) {
            status = GameStatus.WIN;
            winner = turn;
            return MoveResult.win(turn);
        }
        if (board.isFull()) {
            status = GameStatus.DRAW;
            return MoveResult.draw();
        }
        turn = turn == Color.RED ? Color.YELLOW : Color.RED;
        return MoveResult.inProgress();
    }

    Color winner() { return winner; }
}

public class ConnectFourDemo {
    public static void main(String[] args) {
        Game game = new Game(new Board(6, 7), new WinChecker(4));
        System.out.println(game.play(99));
        for (int column : new int[] {0, 1, 0, 1, 0, 1, 0}) {
            System.out.println(column + " -> " + game.play(column));
        }
    }
}

Walkthrough

play(99) returns failed INVALID_COLUMN while IN_PROGRESS. The turn stays red. Then columns 0, 1, 0, 1, 0, 1, 0 alternate red and yellow. Red's fourth disc in column 0 is the bottom four rows, so the last call returns WIN RED. A later play returns GAME_OVER.

Extension to mention

Rows, columns, and win length are already constructor arguments. If asked, say you would keep new Board(rows, cols) and new WinChecker(k) and you would not hardcode 6, 7, and 4 inside Game.

Follow-up questions

  • Why is the win check O(K) per direction, and when would you scan the whole board?
  • What changes if Board owns column validation and Game only owns the turn?
  • Why is there no Player type?
  • What if two clients call play? Synchronize the method. Do not lock inside Board and again inside Game in opposite orders.
  • How would undo work? A stack of placed cells, not a copy of the win checker.

Further extensions

  • Undo, listed only.
  • A bot behind MoveStrategy, listed only. play still validates the chosen column.

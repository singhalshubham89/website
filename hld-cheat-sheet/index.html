Delivery Framework

How to spend a 45-minute high level design interview. The first 37 minutes are fixed. The last 8 minutes flex: answer an extensibility question if the interviewer asks one, otherwise summarize what you drew.

45-minute clock

Talk and draw. Do not design a REST catalog, and do not open with a tool name. Scale is one or two round numbers inside the first five minutes, not its own phase.

PhaseClockWhat you do
Clarify0–5Users, the happy path, functional needs, and what is out of scope. One or two round numbers: reads per second, and how much you store.
Core entities and API5–12The nouns the system stores, who owns each, and the few entry points that read or write them. One line per entry point. Stop before request bodies and status codes.
HLD12–27The picture. Name each service, the one job it owns, and how it connects to the next: a call, a queue, or a store. Mark the read path and the write path.
Deep dive27–37One or two services the interviewer cares about, usually the data store or the hot path. State the tradeoff out loud.
Close37–45If they ask how it grows, answer that extension and do not build it. If they do not, summarize the picture, name one failure, and stop.

Worked timing: URL shortener

Same phases, filled in for a link shortener. A news feed or a chat app would name different nouns. They would not start with a redirect.

  • Clarify. Create a short link, redirect, custom alias optional, no analytics in v1. Writes are rare, redirects dominate, storage is small.
  • Core entities and API. A link is (code, long_url). Entry points: create a link, open a short code.
  • HLD. A stateless link service owns both entry points. The write path stores the row in SQL. The read path checks the cache, then SQL, then redirects.
  • Deep dive. How the code is chosen, cache-aside on redirect, and what happens when the code is missing.
  • Close. If asked, name analytics later via a queue and do not design it. Otherwise summarize the picture and one failure: a duplicate create, or a hot link.

The full walkthrough is in URL shortener.

Done checklist and traps

Stop when these are true:

  • Users, the happy path, and out-of-scope items are written down.
  • One or two scale numbers are written down.
  • Entities and the entry points exist before the picture.
  • The picture names each service, its one job, the read path, and the write path.
  • One deep dive states a tradeoff.
  • Close either answers one extension or summarizes the picture and one failure.

Traps that cost the round:

  • Jumping to Kafka before requirements.
  • Designing endpoints before the entities exist.
  • Drawing the HLD before the read path and the write path are named.

Concepts

The ideas behind the picture. Each card is one sentence, a diagram, when to use it, when to skip it, and the phrase that should make you reach for it.

Start here

Numbers

Round hard. A daily count is not a per-second count, and a user count is not a request count. Clarify uses this card. There is no separate estimate phase.

What you hearWhat you write
1 million requests a dayAbout 12 per second. Peak is often 2–5× the average, unless the product is a ticket drop or a live event.
100 million usersNot 100 million requests per second. Use daily active users × actions per day ÷ 86,400, then apply the peak factor.
A read that must join five tables on the hot pathThat read will not stay fast. Store the answer the way it is read, or cache it.

Pattern: The interviewer gives users, posts, or videos per day and waits for you to turn that into requests per second and storage.

How a request moves

Networking

A request is a path, not a single hop. DNS finds the address, a CDN can answer for public content, a load balancer picks a machine, and any app server can handle it because the servers do not keep the user in memory.

Static and public files can stop at the CDN. A user-specific request continues to an app server.

When to use

  • Every design starts here, even if you then skip the CDN.
  • Say the app servers are stateless so the balancer can send the next request anywhere.

When not to use

  • Do not draw DNS, TLS, and a service mesh before the product is clear.
  • Do not keep session data only in one app server’s memory.

Pattern: “Users open the app from anywhere” or “any server should be able to handle the next request.”

API design

Name the contract in a few lines: who calls it, whether it reads or writes, and what comes back. That is enough for HLD. Request bodies and status codes belong in a low level design round.

A retried write needs an idempotency key so the second try does not create a second row.

When to use

  • After the nouns exist. Each entry point reads or writes one of them.
  • Say which writes are safe to retry, and how a list is paged (a cursor, not “return everything”).

When not to use

  • Do not list ten endpoints before you know the entities.
  • Do not spend the HLD phase on JSON fields.

Pattern: “What can the client do?” after you have named the things the system stores.

Data

Data modeling

Write the nouns, who owns each, and the one query that must be fast. Keep a single source of truth. Copy a field only when one read would otherwise join many tables on the hot path.

When to use

  • Normalize when many callers update the same fact and it must stay consistent.
  • Duplicate a field when the hot read cannot afford the join.

When not to use

  • Do not invent tables for features you put out of scope.
  • Do not pick PostgreSQL or DynamoDB before you know the query.

Pattern: “We look this up by id all day” or “this screen must not join five tables.”

Caching

The hot read checks memory before the database. Cache-aside is the default: on a miss, the app reads the database and fills the cache. Say out loud when a slightly old value is acceptable.

The app owns the fill. The database is still the source of truth.

When to use

  • A small set of keys is read far more often than it changes.
  • The screen can tolerate a value that is seconds old, or you delete the cache entry on write.

When not to use

  • Do not cache the only copy of data you cannot lose.
  • Do not cache a query that is different for every user and never repeats.

Pattern: “Redirects are 100× the writes” or “this page is read constantly and changes rarely.” The usual tool is Redis.

Sharding

Split the data so one machine does not hold all of it. The split key comes from how you look the data up. Say which key would get too hot and what you would do about it.

When to use

  • One database cannot hold the rows or the writes, and queries include the split key.
  • On DynamoDB the partition key is this split.

When not to use

  • Do not shard on day one if one machine still has headroom.
  • Do not split on a key you do not have in the query. You would scan every shard.

Pattern: “Billions of rows” or “one user is huge.” Name the hot key before you name the shard count.

Replication

Keep a copy so reads scale and a dead machine does not take the data with it. Leader-follower is the picture: writes go to the leader, reads can go to a follower, and a follower can be a moment behind.

When to use

  • You need to survive one machine dying, or you have more reads than one machine can serve.
  • Send a read to the leader when the user must see their own write immediately.

When not to use

  • A follower does not add write capacity. All writes still hit the leader.
  • Do not promise a follower read is up to date.

Pattern: “What if that database dies?” or “reads are heavy, writes are not.”

Consistency

When the network splits, you choose staying correct or staying up. You do not get both until the split heals. Strong means a read sees the latest write. Eventual means a read can be a few seconds late and then catches up.

When to use

  • Strong when money, inventory, or a unique name must not be double-spent.
  • Eventual when a feed, a counter, or a search index can be a few seconds late.

When not to use

  • Do not say “we need strong consistency” for every box.
  • Do not use an eventual store as the only record of a payment.

Pattern: “Can two people buy the last seat?” or “Can the feed be a few seconds old?”

Object storage

Files and video are blobs. You store the bytes in object storage and the row that points at them in the database. User rows do not go in the blob store.

When to use

  • The thing is large, mostly written once, and fetched by a key.
  • Put a CDN in front when the same file is public and popular.

When not to use

  • Do not store rows you need to query, join, or update in place.
  • Do not send video bytes through the app server if the client can upload to the store directly.

Pattern: “Users upload a photo or a video.” The usual tool is S3.

Between services

Async messaging

Do the slow or the fan-out work off the request. A queue is for one worker group that does the job. A log is for many services that each need their own copy and can read at their own speed.

When to use

  • The user does not need the result before the response returns.
  • A log when several teams each react to the same event. The event stays after it is read.

When not to use

  • Do not put a queue on a path that must answer now, such as a login check.
  • A queue is not a workflow. A long process with timers and retries is a different idea. See Temporal.

Pattern: “Send the email later,” “update search and analytics from the same write,” or “don’t make the user wait.” The usual log is Kafka.

Rate limiting and idempotency

Rate limiting slows a client down so one caller cannot take the whole service. Idempotency makes a retried write safe: the second try with the same key returns the first result and does not create a second row.

When to use

  • A public write, a login, or anything a script can call in a loop.
  • Any create the client might send twice because the network timed out.

When not to use

  • A limit does not replace capacity planning. It only protects the service.
  • Do not make a read idempotent as a special case. Reads are already safe to retry.

Pattern: “What if they click twice?” or “what if one client sends thousands of requests?” A counter for the limit often lives in Redis.

Delivery and growth

Realtime

Polling asks on a timer. A socket stays open so the server can push when something happens. Pick polling when a short delay is fine. Pick a socket when the screen must change as the event happens.

When to use

  • Polling for a status page, a job result, or a feed that can be a few seconds old.
  • A socket for chat, a live cursor, a game, or a trading price.

When not to use

  • Do not hold a socket per user when they only check once a minute.
  • A socket is stateful. The balancer must stick the connection, or a pub/sub layer must fan the message out.

Pattern: “The other person should see the message immediately” versus “refreshing every few seconds is fine.”

Scaling

A bigger machine helps until that machine is full. More machines help when the work can be split and no single piece of state has to live on one box.

When to use

  • Vertical when one database is the bottleneck and it still has a larger size to move to.
  • Horizontal when app servers are stateless, or the data is already sharded.

When not to use

  • Do not add ten app servers in front of one database and call the system scaled.
  • Do not shard before you have measured that one machine is not enough.

Pattern: “Traffic doubled” or “we cannot buy a bigger database.” Ask which box is full before you add boxes.

Technologies

The tools to say out loud, each tied to a concept. A cousin product gets one sentence on the matching card. You rarely need Kafka, Flink, and Zookeeper in the same answer. Name the one whose job you actually need.

PostgreSQL

Serves data modeling. Source of truth for rows you query in more than one way, with transactions.

When to use

  • The queries are not all “get by this one key,” and a write must be all-or-nothing.
  • The data fits one primary, plus followers for read scale. See replication.

When not to use

  • A single known-key lookup at a write rate one machine cannot take. Look at DynamoDB.
  • Full-text search across millions of documents. Look at Elasticsearch.

Pattern: “We need a unique code, a foreign key, and a transaction.”

DynamoDB

Serves data modeling and sharding. One known key lookup at huge scale. The partition key is the shard key.

When to use

  • You know the access pattern up front: get item, or query one partition.
  • You need that lookup to keep working as the table grows, without running the database yourself.

When not to use

  • Ad-hoc filters, joins, and “sort the whole table.”
  • A key that almost all traffic hits. That partition becomes the ceiling.

Pattern: “Look up by user id at huge scale.” Cassandra is the wide-column cousin you run yourself. Same rule: query by the partition key. It does not get its own card.

Redis

Serves caching. Hot keys, counters, and short-lived locks. Not the place you store the only copy of a user’s data.

When to use

  • The same keys are read constantly, or you need an atomic counter for a rate limit.
  • A lock that must disappear if the owner crashes. Give it a short TTL.

When not to use

  • The only copy of orders, users, or money.
  • A dataset bigger than memory, or a query you would write in SQL.

Pattern: “This read is hot” or “count requests per user per minute.”

Elasticsearch

Serves data modeling for search. Find words and filters fast. The database remains the source of truth. Rebuild the index from it.

A write updates the database first. The index can be a few seconds behind.

When to use

  • Full text, typo-tolerant search, or filters and facets across a large catalog.
  • You can replay the database, or a Kafka log, to rebuild the index.

When not to use

  • As the only store of a record the business cannot lose.
  • A simple “get by primary key.” That is the database, or Redis.

Pattern: “Search products by name, filter by price, show facets.”

Kafka

Serves async messaging. A durable log many services can read at their own speed. The event stays after it is read.

When to use

  • Several services must each react to the same fact, and they must not slow the writer.
  • You may replay history. Order is per partition, so put related events on the same key.

When not to use

  • One worker and a simple job. A queue is enough.
  • A request that must finish before you respond. And do not add Zookeeper just because you added Kafka.

Pattern: “When a link is clicked, analytics, search, and notifications all need the event, on their own schedule.”

Flink

Serves async messaging, the compute step. Stateful processing over a log: windows and aggregates. Kafka stores the stream. Flink calculates on it.

When to use

  • You must count, join, or window a stream continuously, and the state has to survive a crash.
  • The input is already a log, usually Kafka.

When not to use

  • A nightly report. A scheduled query is simpler.
  • A single consumer that sends one email per event. That is a worker, not Flink.

Pattern: “Rolling count of clicks per link for the last five minutes, and it must not reset when a machine dies.”

Temporal

Serves durable workflows: a long process with retries, timers, and steps that must finish even if a server dies. Neighbor idea: async messaging. Temporal is not a replacement for Kafka.

When to use

  • A business process has several steps, some of which wait, and each step must not run twice by accident.
  • The process can last minutes or days, longer than one request.

When not to use

  • Fan-out to many independent consumers. That is Kafka.
  • A single database transaction that finishes in milliseconds.

Pattern: “Take the payment, wait until the item ships, then email, and do not lose your place if we deploy.”

Zookeeper

Serves coordination: who is the leader, and shared config. Kafka moves data. Zookeeper decides who is in charge. etcd is the usual modern stand-in. You do not add Zookeeper because you added Kafka.

When to use

  • A cluster must agree on one leader, a membership list, or a small piece of config.
  • The data is tiny and is read more than it is written.

When not to use

  • As a database for user rows, or as a queue for events.
  • As a required companion to a new Kafka design. Say the coordination problem on its own.

Pattern: “Only one node should run this job” or “everyone must see the same config.”

S3

Serves object storage. Images, video, and big files. Not user rows.

When to use

  • A file is large, written once, and downloaded by key.
  • You want the client to upload directly, so the bytes do not pass through the app.

When not to use

  • Records you update field by field, or query with SQL.
  • A tiny config value many services must watch. That is coordination, not a blob.

Pattern: “Store the video” or “the image is 4 MB and we only need it by id.”

URL shortener

Problem

A person pastes a long URL and gets back a short code. Anyone who opens that code is sent to the long URL. A custom code is optional. Analytics, accounts, and link expiry are out of scope for v1.

Clarify

  • Users: someone who creates a link, and anyone who opens it. No login in v1.
  • Happy path: create returns a code. Opening the code redirects.
  • Out of scope: click charts, user accounts, expiry, and a preview image.
  • Scale, rounded: writes are rare, redirects dominate. Storage is one small row per link, so it stays small next to the read traffic. Say “reads are about 100× writes” and move on.

Core entities and API

One noun: a link, (code, long_url). The link service owns it.

  • Create a link. Write. In: the long URL, and an optional custom code. Out: the code.
  • Open a short code. Read. In: the code. Out: a redirect to the long URL, or not found.

Creating the same long URL twice may return two codes. Say that, so dedupe is a choice and not an accident. A custom code must be unique.

HLD

One stateless service owns both entry points. Any machine can take the next request. The write path inserts the row in PostgreSQL. The read path checks Redis, then PostgreSQL, then redirects.

Green dot: open a code. Create skips Redis and inserts the row.

  • Write. Validate the URL, choose a code, insert. Unique constraint on code rejects a custom alias that is taken.
  • Read. Cache, then database, then redirect. The app servers store nothing locally.

Deep dive

How the code is chosen. A random 7-character code from a URL-safe alphabet, with a retry if the unique constraint fails, is enough at this size. A counter from one allocator avoids the retry. Say which one you pick. Do not build both.

Cache-aside on redirect. Key is the code. Value is the long URL. On a hit, redirect. On a miss, read PostgreSQL, fill Redis, redirect. Links rarely change, so a long TTL is fine. Do not cache “missing” for long, or a typo sticks.

Missing code. Return not found. Do not redirect to a default page that hides a bad link.

Tradeoff. PostgreSQL is the source of truth because the code must be unique and the row is tiny. Redis exists only because the read is hot. If Redis is empty, redirects get slower and the database must survive that spike. That is acceptable. Losing Redis must not lose links.

Close

Summarize: one service, one SQL row, cache on the read path.

One failure. A hot link is fine while Redis holds it. If Redis restarts, that one code hits PostgreSQL until the cache fills again. A second failure to mention if asked: two creates of the same long URL produce two codes, unless you decided to dedupe.

If they ask how it grows. Click analytics is a write on the read path, so do not count it in PostgreSQL during the redirect. Publish a click event to Kafka and let a consumer count it. Name that. Do not design the pipeline unless they ask you to stay there. Flink is the follow-up only if they want a rolling count.
